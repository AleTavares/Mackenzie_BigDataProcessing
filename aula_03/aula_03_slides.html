Formatos de Arquivo

Trade-offs entre CSV, JSON, Parquet, ORC, Avro e Delta

MACKENZIE

📄 Por Que o Formato Importa em Big Data?

Em processamento distribuído, o formato do arquivo impacta diretamente: velocidade de leitura, compressão, suporte a schema e paralelismo.

O cenário da DataFlow:

  • Parceiro A: CSV — simples, mas sem tipos, sem compressão, lento
  • Parceiro B: JSON — flexível, mas verboso e sem otimização de coluna
  • Parceiro C: Parquet — otimizado, mas exige ferramentas específicas
CategoriaFormatosCaracterística
TextoCSV, JSON, XMLLegíveis por humanos, sem otimização
Colunar binárioParquet, ORCOtimizados para analytics
Row-based binárioAvroOtimizado para escrita e streaming
TransacionalDelta, Iceberg, HudiACID + time travel + schema evolution
MACKENZIE

📋 CSV — Comma Separated Values

Formato mais antigo e universalmente suportado. Ideal para interoperabilidade, mas péssimo para performance em big data.

Vantagens

  • ✅ Legível por humanos (texto plano)
  • ✅ Qualquer ferramenta lê (Excel, Python, Shell)
  • ✅ Fácil debug e inspeção manual

Desvantagens

  • ❌ Sem tipos — tudo é string
  • ❌ Sem compressão nativa
  • ❌ Leitura completa — todas as colunas sempre
  • ❌ Sem schema embutido
# Parceiro A: CSV legado com peculiaridades
df_csv = spark.read.csv(
    "data/parceiro_a/*.csv",
    header=True,              # Primeira linha é header
    sep=";",                  # Separador ponto-e-vírgula
    encoding="ISO-8859-1",   # Encoding latin (acentos)
    inferSchema=True,         # Tentar inferir tipos (LENTO em produção!)
    nullValue="N/A",          # String que representa null
    dateFormat="dd/MM/yyyy"   # Formato de data brasileiro
)
MACKENZIE

🔗 JSON — JavaScript Object Notation

Formato padrão de APIs REST. Excelente para dados semiestruturados e hierárquicos, mas verboso e ineficiente para analytics.
  • ✅ Suporta dados aninhados (nested objects, arrays)
  • ✅ Schema flexível por registro
  • ✅ Padrão universal de APIs web
  • ❌ Verboso — overhead de chaves repetidas
  • ❌ Sem compressão nativa
  • ❌ Não é splittable (multiLine)
  • ❌ Parsing lento
# Parceiro B: JSON de API dumps
df_json = spark.read.json("data/parceiro_b/*.json", multiLine=True)

# Flatten de dados aninhados
from pyspark.sql.functions import explode, col
df_flat = df_json.select(
    col("cliente_id"),
    explode(col("pedidos")).alias("pedido")
).select(
    col("cliente_id"),
    col("pedido.id").alias("order_id"),
    col("pedido.valor").alias("total_amount")
)

JSON Lines (JSONL) — cada linha é um JSON independente → splittable → paralelismo possível.

🏛️ Parquet — O Padrão do Data Lake

Apache Parquet armazena dados por coluna, otimizando drasticamente leituras analíticas.
ROW-BASED (CSV, JSON, Avro):          COLUNAR (Parquet, ORC):
┌──────┬────────┬────────┬─────┐      ┌──────────────────────────┐
│ id   │ nome   │ cidade │valor│      │ id:  1, 2, 3, 4, 5 ...  │
├──────┼────────┼────────┼─────┤      ├──────────────────────────┤
│ 1    │ João   │ SP     │ 150 │      │ nome: João, Maria, ...   │
│ 2    │ Maria  │ RJ     │ 200 │      ├──────────────────────────┤
│ 3    │ Pedro  │ MG     │ 350 │      │ cidade: SP, RJ, MG ...   │
└──────┴────────┴────────┴─────┘      ├──────────────────────────┤
Para ler só "valor":                   │ valor: 150, 200, 350 ... │
Precisa ler TUDO (4 colunas)           └──────────────────────────┘
                                       Para ler só "valor":
                                       Lê APENAS a coluna "valor"
  • ✅ Column pruning — lê apenas colunas solicitadas
  • ✅ Compressão excelente (Snappy, GZIP, ZSTD)
  • ✅ Schema embutido — metadados no arquivo
  • ✅ Predicate pushdown — filtra antes de ler
  • ✅ Splittable — paralelismo total
MACKENZIE

📦 ORC e Avro — Quando Usar?

ORC (Optimized Row Columnar)

  • ✅ Excelente compressão
  • ✅ Suporte nativo a ACID no Hive
  • ✅ Bloom filters embutidos
  • ❌ Ecossistema menor fora do Hadoop
  • 📌 Usar: ecossistema Hive/Hadoop

Avro (Row-based binário)

  • ✅ Schema evolution nativa
  • ✅ Compacto e binário
  • ✅ Excelente para Kafka/streaming
  • ✅ Splittable
  • ❌ Sem column pruning
  • 📌 Usar: streaming, event sourcing
# Leitura de Avro (requer spark-avro package)
df_avro = spark.read.format("avro").load("data/events/")

# Leitura de ORC
df_orc = spark.read.orc("data/hive_tables/vendas/")
Regra prática: No ecossistema Spark moderno, Parquet é a escolha padrão. Use Avro para streaming e ORC se já está no Hive.
MACKENZIE

🔺 Delta Lake — Parquet + ACID + Time Travel

Delta Lake é uma camada sobre Parquet que adiciona transações ACID, time travel, e schema enforcement. Padrão para lakehouse moderno.
DELTA LAKE = PARQUET + EXTRAS

Parquet files (dados)        + _delta_log/ (transaction log)
┌─────┐ ┌─────┐ ┌─────┐      ┌──────────────────────────────┐
│.parq│ │.parq│ │.parq│      │ 000000.json (commit 0)       │
└─────┘ └─────┘ └─────┘      │ 000001.json (commit 1)       │
                              │ 000002.json (commit 2)       │
                              └──────────────────────────────┘
  • ✅ ACID transactions (leitura consistente durante escrita)
  • ✅ Time Travel (acessar versões anteriores)
  • ✅ Schema enforcement + Schema evolution
  • ✅ MERGE (upsert: update + insert em uma operação)
  • ✅ DELETE/UPDATE (impossíveis em Parquet puro)
# Time travel: ler versão anterior
df_ontem = spark.read.format("delta") \
    .option("versionAsOf", 2) \
    .load("datalake/silver/vendas/")

df.write.parquet("output/", compression="snappy")   # Default, rápido
df.write.parquet("output/", compression="gzip")     # Menor, mais lento

MACKENZIE

🥇🥈🥉 Arquitetura Medallion — Conceito

A Arquitetura Medallion organiza o data lake em 3 camadas progressivas de qualidade e transformação.
FONTES              BRONZE           SILVER            GOLD
┌─────┐          ┌────────┐       ┌────────┐       ┌────────┐
│CSV  │─ingest─►│ Raw    │─clean─►│Unified │─agg──►│Business│
│(A)  │          │ As-Is  │       │Validated│       │ Ready  │
└─────┘          └────────┘       └────────┘       └────────┘
┌─────┐          ┌────────┐
│JSON │─ingest─►│ Raw    │───────►
│(B)  │          │ As-Is  │
└─────┘          └────────┘
┌─────┐          ┌────────┐
│Parq │─ingest─►│ Raw    │───────►
│(C)  │          │ As-Is  │
└─────┘          └────────┘

QUALIDADE:  Baixa ──────────────────────────────────► Alta
SCHEMA:     Original ──► Normalizado ──► Desnormalizado
FORMATO:    Qualquer ──► Parquet/Delta ──► Parquet/Delta
AUDIÊNCIA:  Eng. Dados ─► Eng. Dados ──► Analistas/BI
MACKENZIE

🥉 Bronze — "Ingira Tudo, Transforme Nada"

A camada Bronze armazena os dados exatamente como chegaram da fonte, acrescidos de metadados de ingestão.
  • ✅ Sem transformação — dados brutos, fiéis à origem
  • ✅ Append-only — nunca sobrescrever ou deletar
  • ✅ Adicionar metadados: timestamp de ingestão, fonte, arquivo
  • ❌ Sem validação de negócio
  • ❌ Sem deduplicação
from pyspark.sql.functions import lit, current_timestamp, input_file_name

# Ingestão do Parceiro A (CSV legado)
df_bronze_a = spark.read.csv(
    "data/parceiro_a/*.csv",
    header=True, sep=";", encoding="ISO-8859-1"
).withColumn("_source", lit("parceiro_a")) \
 .withColumn("_ingestion_ts", current_timestamp()) \
 .withColumn("_file_origin", input_file_name())

# Salvar na Bronze — preservar sem alterar
df_bronze_a.write.mode("append").parquet("datalake/bronze/parceiro_a/")
MetadadoTipoPropósito
_sourcestringIdentificar parceiro/sistema de origem
_ingestion_tstimestampQuando o dado foi ingerido
_file_originstringQual arquivo gerou o registro
MACKENZIE

🥈 Silver — "Dados Limpos e Unificados"

A camada Silver normaliza schemas, aplica validações, remove duplicatas e unifica dados de diferentes fontes.
  • ✅ Unificação de schemas — mesmas colunas, mesmos tipos
  • ✅ Deduplicação — remover registros duplicados
  • ✅ Validação — rejeitar/quarentena dados inválidos
  • ✅ Conversão de tipos — strings para dates, decimals
from pyspark.sql.functions import col, to_timestamp, upper, trim

# Normalização: cada parceiro → schema unificado
df_silver_a = df_bronze_a.select(
    col("codigo_pedido").alias("order_id"),
    col("cod_cliente").alias("customer_id"),
    to_timestamp(col("data_pedido"), "dd/MM/yyyy").alias("order_date"),
    col("valor_total").cast("double").alias("total_amount"),
    upper(trim(col("estado"))).alias("shipping_state"),
    lit("parceiro_a").alias("source")
)

# Unificar as 3 fontes normalizadas
df_silver = df_silver_a.unionByName(df_silver_b).unionByName(df_silver_c)

# Validações de negócio
df_valid = df_silver.filter(
    (col("total_amount") > 0) &
    (col("order_date").isNotNull()) &
    (col("order_id").isNotNull())
)
MACKENZIE

🥇 Gold — "Pronto para Decisão de Negócio"

A camada Gold contém dados agregados, desnormalizados e otimizados para consumo direto por analistas, dashboards e ML.
  • ✅ Desnormalizado — joins já feitos, pronto para query
  • ✅ Agregado — métricas pré-calculadas
  • ✅ Otimizado — particionado para queries comuns
  • 📌 Audiência: Analistas, BI, Data Scientists
from pyspark.sql.functions import sum as spark_sum, count, avg as spark_avg

# Gold: Faturamento diário por parceiro e estado
df_gold = df_silver_valid.groupBy(
    col("order_date").cast("date").alias("data"),
    "source", "shipping_state"
).agg(
    spark_sum("total_amount").alias("faturamento"),
    count("order_id").alias("total_pedidos"),
    spark_avg("total_amount").alias("ticket_medio")
)

# Persistir na Gold (particionado para BI)
df_gold.write.mode("overwrite") \
    .partitionBy("data") \
    .parquet("datalake/gold/faturamento_diario/")

Particionamento

Organizar dados para performance de leitura

MACKENZIE

📂 Particionamento — Conceito Fundamental

Particionamento divide os dados em subdiretórios baseados no valor de uma coluna. Permite ao Spark ler apenas os dados relevantes (partition pruning).
Sem particionamento:                Com particionamento por data:
vendas/                             vendas/
├── part-00000.parquet (MIX)        ├── order_date=2023-06-14/
├── part-00001.parquet (MIX)        │   └── part-00000.parquet
└── part-00002.parquet (MIX)        ├── order_date=2023-06-15/  ← Spark lê SÓ AQUI!
                                    │   └── part-00000.parquet
WHERE order_date = '2023-06-15'     └── order_date=2023-06-16/
→ Abre TODOS os 3 arquivos              └── part-00000.parquet

                                    WHERE order_date = '2023-06-15'
                                    → Lê APENAS 1 diretório = 3x mais rápido!

# Salvar com particionamento
df_vendas.write.mode("overwrite") \
    .partitionBy("order_date") \
    .parquet("datalake/silver/vendas/")

# Spark faz partition pruning automaticamente na leitura
df = spark.read.parquet("datalake/silver/vendas/")
df.filter(col("order_date") == "2023-06-15").explain()
# Plano mostra: PartitionFilters: [order_date = 2023-06-15]

A escolha errada de particionamento pode piorar a performance. Particione por colunas que aparecem frequentemente em filtros (WHERE).

⚠️ Small Files Problem e Over-Partitioning

O erro mais comum em data lakes: partições com arquivos muito pequenos. Cada Parquet deve ter entre 128MB e 1GB.
❌ OVER-PARTITIONING (particionar por customer_id):
vendas/
├── customer_id=C00001/
│   └── part-00000.parquet  (2 KB — 3 registros!)
├── customer_id=C00002/
│   └── part-00000.parquet  (1 KB — 2 registros!)
└── ... (500.000 diretórios!)

RESULTADO: 500K chamadas ao filesystem, driver OOM, Spark ineficiente

✅ PARTICIONAMENTO CORRETO (por data):
vendas/
├── order_date=2023-06-14/
│   └── part-00000.parquet  (150 MB — 100K registros)
├── order_date=2023-06-15/
│   └── part-00000.parquet  (145 MB — 98K registros)

RESULTADO: 365 diretórios/ano, arquivos de tamanho ideal
Regras de ouro: 📏 Arquivo ideal: 128MB — 1GB · 📂 Máximo: 10.000 partições · 🛠️ Use coalesce() para controlar arquivos por partição 
# Controlar tamanho dos arquivos
df.repartition(1).write.partitionBy("order_date") \
    .parquet("output/")  # 1 arquivo por partição de data

Schema Evolution

Quando a fonte muda — e ela sempre muda

MACKENZIE

🔄 Schema Evolution — Quando a Fonte Muda

Em produção, schemas mudam inevitavelmente. Novos campos são adicionados, tipos mudam. O pipeline precisa lidar com isso sem quebrar.
Semana 1: Parceiro B envia JSON com 5 campos
{"order_id": "V001", "customer_id": "C001", "amount": 150,
 "date": "2023-01-15", "status": "delivered"}

Semana 5: Parceiro B adiciona "discount"
{"order_id": "V100", ..., "status": "shipped", "discount": 15.0}

Semana 8: Parceiro B adiciona "payment_method"
{"order_id": "V200", ..., "discount": 0, "payment_method": "pix"}

# Sem schema evolution → ERRO!
df_novo.write.mode("append").parquet("datalake/silver/vendas/")
# AnalysisException: Cannot write incompatible data:
#   Extra column: discount (DoubleType)
AbordagemComportamentoQuando usar
Schema EnforcementRejeita dados com schema diferenteGold layer, dados críticos
Schema EvolutionAceita novos campos automaticamenteBronze/Silver, fontes mutáveis
MACKENZIE

🔒 Enforcement vs 🔓 Evolution

Schema Enforcement

# Parquet puro: enforcement é default
df_novo.write.mode("append") \
    .parquet("output/")
# Colunas extras → ERRO

# Delta: enforcement explícito
df_novo.write.format("delta") \
    .mode("append") \
    .save("datalake/gold/vendas/")

Schema Evolution

# Parquet: merge schemas ao LER
df = spark.read \
    .option("mergeSchema", "true") \
    .parquet("datalake/silver/")
# Colunas novas → null nos antigos

# Delta: evolution ao ESCREVER
df_novo.write.format("delta") \
    .option("mergeSchema", "true") \
    .mode("append") \
    .save("datalake/silver/")
MudançaParquet (mergeSchema)Delta Lake
Adicionar coluna✅✅
Remover coluna⚠️ (fica null)✅ (configurável)
Mudar tipo (int → long)❌✅ (widening)
Mudar tipo (string → int)❌❌ (incompatível)
Renomear coluna❌❌ (trata como nova)
Estratégia DataFlow: Bronze = evolution ativado · Silver = evolution controlado · Gold = enforcement fixo

🔀 MERGE — Update + Insert em Uma Operação

MERGE (upsert) atualiza registros existentes e insere novos em uma única operação atômica. Disponível com Delta Lake.
# O problema sem merge:
# Com append → DUPLICATA! (V001 aparece 2x com status diferente)
# Com overwrite → PERDE dados de outros dias!
from delta.tables import DeltaTable

delta_vendas = DeltaTable.forPath(spark, "datalake/silver/vendas/")
df_novos = spark.read.json("data/parceiro_b/2023-06-16/*.json")

# MERGE: atualiza se existe, insere se não existe
delta_vendas.alias("target").merge(
    df_novos.alias("source"),
    "target.order_id = source.order_id"
).whenMatchedUpdate(set={
    "status": col("source.status"),
    "total_amount": col("source.total_amount"),
    "updated_at": current_timestamp()
}).whenNotMatchedInsertAll() \
  .execute()

📐 Anatomia de um Arquivo Parquet

┌─────────────────────────────────────────────────────────────────┐
│ ROW GROUP 1 (tipicamente 128MB)                                  │
│  ┌────────────────────────────────────────────────────────────┐ │
│  │ Column Chunk: order_id     [min:"V001", max:"V999"]        │ │
│  │ Column Chunk: customer_id  [min:"C001", max:"C500"]        │ │
│  │ Column Chunk: total_amount [min: 10.0,  max: 5000.0]      │ │
│  │ Column Chunk: order_date   [min:"2023-01", max:"2023-06"]  │ │
│  └────────────────────────────────────────────────────────────┘ │
├─────────────────────────────────────────────────────────────────┤
│ ROW GROUP 2                                                      │
│  ┌────────────────────────────────────────────────────────────┐ │
│  │ Column Chunk: total_amount [min: 5.0,   max: 8000.0]      │ │
│  │ Column Chunk: order_date   [min:"2023-07", max:"2023-12"]  │ │
│  └────────────────────────────────────────────────────────────┘ │
├─────────────────────────────────────────────────────────────────┤
│ FOOTER (metadata)                                                │
│  - Schema completo (nomes, tipos)                               │
│  - Estatísticas por row group (min, max, null_count)            │
│  - Offsets para cada column chunk                               │
└─────────────────────────────────────────────────────────────────┘

Como o Spark otimiza:
Query: WHERE total_amount > 6000
→ Row Group 1: max=5000 → SKIP (não precisa ler!)
→ Row Group 2: max=8000 → LER (pode ter registros)
= Lê apenas 50% dos dados!

⚡ Partition Pruning + Predicate Pushdown

Query: df.filter(col("order_date") == "2023-06-15")
           .filter(col("total_amount") > 1000)
           .select("order_id", "customer_id", "total_amount")

ETAPA 1: Partition Pruning (filesystem)
  vendas/
  ├── order_date=2023-06-14/ ← SKIP
  ├── order_date=2023-06-15/ ← LER ✅
  └── order_date=2023-06-16/ ← SKIP

ETAPA 2: Row Group Filtering (Parquet metadata)
  Dentro de order_date=2023-06-15/:
  Row Group 1: total_amount [min:10, max:500]  ← SKIP
  Row Group 2: total_amount [min:200, max:5000] ← LER ✅

ETAPA 3: Column Pruning
  Dentro do Row Group 2, ler apenas:
  ✅ order_id
  ✅ customer_id
  ✅ total_amount
  ❌ status (não solicitado → não lido)
  ❌ shipping_state (não solicitado → não lido)

RESULTADO: Leu ~5% dos dados totais!
