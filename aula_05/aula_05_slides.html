Branching Condicional

BranchPythonOperator — decisões automáticas no pipeline

MACKENZIE

🔀 BranchPythonOperator — Conceito

BranchPythonOperator executa uma função que retorna o task_id da próxima task a executar. Tasks não selecionadas são marcadas como skipped.
FLUXO DE BRANCHING:

                         ┌── "process_weekday" ──► [transform_full]
[check_day_of_week] ────►│
                         └── "process_weekend" ──► [transform_light]
                                                         │
                                                         ▼
                                                    [join_point]

• check_day_of_week retorna "process_weekday" OU "process_weekend"
• A branch NÃO selecionada fica com status SKIPPED
• join_point precisa de trigger_rule="none_failed_min_one_success"
Regra fundamental: A função do Branch deve retornar um task_id (string) ou lista de task_ids. Tasks fora da lista são automaticamente skipped.
MACKENZIE

🔀 BranchPythonOperator — Implementação

from airflow.operators.python import BranchPythonOperator
from datetime import datetime

def choose_branch(**kwargs):
    """Decide qual caminho seguir baseado no dia da semana."""
    execution_date = kwargs["execution_date"]
    day_of_week = execution_date.weekday()  # 0=seg, 6=dom
    
    if day_of_week >= 5:  # Sábado ou Domingo
        return "skip_parceiro_b"  # Parceiro B não envia no fim de semana
    else:
        return "ingest_parceiro_b"

with DAG(...) as dag:
    branch = BranchPythonOperator(
        task_id="check_day_of_week",
        python_callable=choose_branch
    )
    
    ingest_b = PythonOperator(task_id="ingest_parceiro_b", ...)
    skip_b = DummyOperator(task_id="skip_parceiro_b")
    
    join = DummyOperator(
        task_id="join_after_branch",
        trigger_rule="none_failed_min_one_success"  # Importante!
    )
    
    branch >> [ingest_b, skip_b] >> join >> transform

📊 Branching por Volume de Dados

def choose_cluster_size(**kwargs):
    """Seleciona cluster baseado no volume esperado."""
    ti = kwargs["ti"]
    records = ti.xcom_pull(task_ids="count_records")
    
    if records > 1_000_000:
        return "spark_large_cluster"   # 8 workers
    elif records > 100_000:
        return "spark_medium_cluster"  # 4 workers
    else:
        return "spark_small_cluster"   # 2 workers

branch_volume = BranchPythonOperator(
    task_id="check_volume",
    python_callable=choose_cluster_size
)

spark_large = BashOperator(
    task_id="spark_large_cluster",
    bash_command="spark-submit --num-executors 8 /jobs/transform.py --date {{ ds }}"
)
spark_medium = BashOperator(
    task_id="spark_medium_cluster",
    bash_command="spark-submit --num-executors 4 /jobs/transform.py --date {{ ds }}"
)
spark_small = BashOperator(
    task_id="spark_small_cluster",
    bash_command="spark-submit --num-executors 2 /jobs/transform.py --date {{ ds }}"
)

count >> branch_volume >> [spark_large, spark_medium, spark_small] >> join

Sensors

Esperando eventos externos — arquivos, APIs, outras DAGs

MACKENZIE

👁️ Sensors — Esperando o Mundo Exterior

Sensors são operators especiais que ficam esperando uma condição ser verdadeira antes de liberar a execução. Polling até sucesso ou timeout.
SensorEspera por...Caso de uso
FileSensorArquivo aparecer no pathParceiro deposita arquivo
ExternalTaskSensorTask de outra DAG completarDependência entre DAGs
HttpSensorEndpoint retornar 200API disponível
S3KeySensorObjeto aparecer no S3Arquivo no cloud storage
SqlSensorQuery retornar resultadoDados prontos no DB
TimeDeltaSensorTempo passarEsperar N minutos
Comportamento do Sensor:

[Sensor] ──poke──► condição falsa ──► espera (poke_interval) ──► poke novamente
                   condição falsa ──► espera ──► poke novamente
                   condição TRUE  ──► ✅ SUCESSO → próxima task executa
                   timeout         ──► ❌ FALHA (ou soft_fail → skip)
MACKENZIE

📁 FileSensor — Esperando Arquivos do Parceiro

from airflow.sensors.filesystem import FileSensor

# Esperar arquivo do Parceiro C (horário imprevisível)
wait_for_file = FileSensor(
    task_id="wait_parceiro_c_file",
    filepath="/data/incoming/parceiro_c/{{ ds }}/export.parquet",
    poke_interval=300,        # Verificar a cada 5 minutos
    timeout=3600 * 6,         # Timeout após 6 horas
    mode="poke",              # poke = ocupa worker slot
    soft_fail=True            # Se timeout → SKIP (não FAIL)
)

# Esperar qualquer arquivo .csv no diretório
wait_csv = FileSensor(
    task_id="wait_any_csv",
    filepath="/data/incoming/parceiro_a/{{ ds }}/*.csv",
    fs_conn_id="fs_default",
    poke_interval=60,
    timeout=7200,
    mode="reschedule"         # reschedule = libera worker entre pokes
)

# Fluxo
wait_for_file >> ingest_parceiro_c >> transform
mode="poke" vs "reschedule": Poke mantém o worker ocupado (bom para esperas curtas). Reschedule libera o slot entre verificações (bom para esperas longas).
MACKENZIE

🔗 ExternalTaskSensor — Dependências entre DAGs

Quando uma DAG depende da conclusão de outra DAG (ou task específica de outra DAG).

📦 TaskGroups — Organização de Tasks

TaskGroups agrupam tasks visualmente na UI sem criar sub-DAGs. Melhoram legibilidade de pipelines complexos.
from airflow.utils.task_group import TaskGroup

with DAG(...) as dag:
    start = DummyOperator(task_id="start")
    
    # Grupo de Ingestão
    with TaskGroup(group_id="ingest") as ingest_group:
        ingest_a = PythonOperator(task_id="parceiro_a", ...)
        ingest_b = PythonOperator(task_id="parceiro_b", ...)
        ingest_c = PythonOperator(task_id="parceiro_c", ...)
    
    # Grupo de Transformação
    with TaskGroup(group_id="transform") as transform_group:
        silver = BashOperator(task_id="silver", ...)
        gold = BashOperator(task_id="gold", ...)
        silver >> gold
    
    # Grupo de Notificação
    with TaskGroup(group_id="notify") as notify_group:
        slack = PythonOperator(task_id="slack", ...)
        email = PythonOperator(task_id="email", ...)
    
    start >> ingest_group >> transform_group >> notify_group
UI do Airflow (Graph View):
[start] → [📦 ingest] → [📦 transform] → [📦 notify]
              │ expand:        │ expand:
              ├─ parceiro_a    ├─ silver
              ├─ parceiro_b    └─ gold
              └─ parceiro_c

task_transform = SparkSubmitOperator(

    conf={
        "spark.executor.memory": "4g",
        "spark.executor.cores": "2",
        "spark.dynamicAllocation.enabled": "true"

    application_args=[
        "--date", "{{ ds }}",
        "--input", "/datalake/bronze/",
        "--output", "/datalake/silver/"

    num_executors=4,
    executor_memory="4g",
    driver_memory="2g",
    verbose=True
)

📢 Callbacks — Alertas Inteligentes

import requests

def notify_slack_on_failure(context):
    """Envia alerta formatado para Slack quando task falha."""
    dag_id = context["dag"].dag_id
    task_id = context["task_instance"].task_id
    exec_date = context["ds"]
    log_url = context["task_instance"].log_url
    exception = context.get("exception", "Unknown")
    
    payload = {
        "blocks": [
            {"type": "header", "text": {"type": "plain_text",
                "text": f"❌ Pipeline Failure: {dag_id}"}},
            {"type": "section", "fields": [
                {"type": "mrkdwn", "text": f"*Task:* {task_id}"},
                {"type": "mrkdwn", "text": f"*Date:* {exec_date}"},
                {"type": "mrkdwn", "text": f"*Error:* {exception}"},
                {"type": "mrkdwn", "text": f"*Logs:* <{log_url}|View>"}
            ]}
        ]
    }
    requests.post(SLACK_WEBHOOK_URL, json=payload)

def notify_on_dag_success(context):
    """Chamado quando a DAG inteira completa com sucesso."""
    send_slack_message(f"✅ Pipeline {context['dag'].dag_id} OK - {context['ds']}")

with DAG(
    ...,
    on_failure_callback=notify_slack_on_failure,
    on_success_callback=notify_on_dag_success
) as dag:
    ...

def notify_critical(context):
    """Alerta IMEDIATO: SMS + Slack + PagerDuty."""

Trigger Rules

Controle avançado de quando uma task deve executar

MACKENZIE

🎛️ Trigger Rules — Controle de Execução

O trigger_rule define a condição que uma task avalia nos seus upstream para decidir se executa. Default: all_success.
Trigger RuleExecuta quando...Caso de uso
all_successTodos upstream = successDefault, fluxo normal
all_failedTodos upstream = failedTask de recovery
all_doneTodos upstream terminaram (qualquer estado)Cleanup final
one_successPelo menos 1 upstream = successFan-in parcial
one_failedPelo menos 1 upstream = failedAlerta rápido
none_failedNenhum upstream falhou (success ou skip)Após branch
none_failed_min_one_successNenhum falhou + pelo menos 1 sucessoJoin de branch
none_skippedNenhum upstream skippedValidação
MACKENZIE

🔧 Trigger Rules — Exemplos Práticos

from airflow.utils.trigger_rule import TriggerRule

# CENÁRIO 1: Join após branching
join_point = DummyOperator(
    task_id="join",
    trigger_rule=TriggerRule.NONE_FAILED_MIN_ONE_SUCCESS
)

# CENÁRIO 2: Cleanup SEMPRE executa (mesmo se pipeline falhou)
cleanup = PythonOperator(
    task_id="cleanup_temp_files",
    python_callable=cleanup_temp,
    trigger_rule=TriggerRule.ALL_DONE  # Executa SEMPRE
)

# CENÁRIO 3: Alerta se QUALQUER ingestão falhar
alert_on_any_failure = PythonOperator(
    task_id="alert_failure",
    python_callable=send_alert,
    trigger_rule=TriggerRule.ONE_FAILED  # Dispara com 1 falha
)

# CENÁRIO 4: Report só se TODOS parceiros ingeridos com sucesso
generate_report = PythonOperator(
    task_id="full_report",
    python_callable=gen_report,
    trigger_rule=TriggerRule.ALL_SUCCESS  # Precisa de todos
)
[ingest_a] ─┐     trigger_rule=ALL_SUCCESS
[ingest_b] ─┼──►  [full_report]
[ingest_c] ─┘
       │           trigger_rule=ONE_FAILED
       └────────►  [alert_failure]
       │           trigger_rule=ALL_DONE
       └────────►  [cleanup]

🏗️ DAG Avançada — Combinando Tudo

with DAG("pipeline_inteligente_v2", ...) as dag:

    # SENSOR: Esperar arquivo chegar
    wait_file = FileSensor(task_id="wait_file", ...)

        task_id="join",
        trigger_rule="none_failed_min_one_success"
    )
    
    # SPARK: Transform
    spark_transform = SparkSubmitOperator(task_id="spark", ...)
    
    # CLEANUP: sempre executa
    cleanup = PythonOperator(
        task_id="cleanup",
        trigger_rule="all_done"
    )
    
    wait_file >> branch >> [tg_weekday, tg_weekend] >> join
    join >> spark_transform >> cleanup

❌ Anti-Patterns a Evitar

Anti-PatternProblemaSolução
DAGs com 100+ tasksUI lenta, difícil debugarDividir em sub-DAGs ou usar TaskGroups
XCom com DataFramesMetadata DB estouraPassar file paths, não dados
Sensor com mode="poke" longoWorker slot ocupado por horasUsar mode="reschedule"
catchup=True sem limiteCentenas de DAG Runs simultâneasmax_active_runs + catchup=False
Lógica pesada no DAG fileScheduler lento (parse a cada 30s)Lógica em funções importadas
Ignorar trigger_rule após branchTasks downstream ficam skippedUsar none_failed_min_one_success
Hardcoded datesBackfill impossívelUsar {{ ds }} sempre

✅ Boas Práticas — Orquestração Avançada

PráticaPor quê
Use Sensors com mode="reschedule" para esperas longasNão bloqueia worker slots
Defina timeout em todo SensorEvita tasks presas infinitamente
Use soft_fail=True em sensors opcionaisSkip > Fail para dados não-críticos
Agrupe com TaskGroups (não SubDAGs)SubDAGs estão deprecated, TaskGroups são superiores
Use trigger_rule após branchesEvita cascata de skips indesejados
Implemente callbacks por criticidadeNem toda falha merece PagerDuty
Prefira SparkSubmitOperator sobre BashOperatorMonitoramento integrado, connections gerenciadas
Use max_active_runs para limitar concorrênciaEvita sobrecarga do cluster
Teste branches com airflow tasks testValidar lógica antes do deploy
