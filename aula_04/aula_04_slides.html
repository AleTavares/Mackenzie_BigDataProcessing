O que é Apache Airflow?

DAGs, Tasks e Operators — os blocos fundamentais

MACKENZIE

🌬️ Apache Airflow — Visão Geral

Apache Airflow é uma plataforma de orquestração de workflows definidos como código (Python). Criado pelo Airbnb em 2014, é hoje o padrão da indústria para pipelines de dados.
  • Workflows como código — DAGs escritas em Python puro
  • Scheduler inteligente — executa tarefas no horário certo, respeitando dependências
  • UI Web — monitoramento visual em tempo real
  • Extensível — centenas de operadores para qualquer integração
  • Backfill — reprocessar dados históricos facilmente
Airflow NÃO é: framework de processamento (como Spark). Ele orquestra a execução de ferramentas, não processa dados diretamente.

📊 DAG — Directed Acyclic Graph

Directed (Direcionado)

Cada aresta tem direção: A → B significa "A executa antes de B".

Acyclic (Acíclico)

Sem ciclos: impossível A → B → C → A. Garante que o pipeline termina.

Graph (Grafo)

Conjunto de nós (tasks) conectados por arestas (dependências).

✅ VÁLIDO (acíclico):
A → B → D
A → C → D

❌ INVÁLIDO (cíclico):
A → B → C → A

    start_date=datetime(2024, 1, 1),

    catchup=False,
    tags=["dataflow", "production"]

Operators

PythonOperator, BashOperator e o ecossistema

MACKENZIE

🐍 PythonOperator — O Mais Versátil

Executa qualquer função Python como uma task do Airflow. É o operador mais usado e flexível.
from airflow import DAG
from airflow.operators.python import PythonOperator
from datetime import datetime

def ingest_parceiro_a(**kwargs):
    """Função que será executada como task."""
    execution_date = kwargs["ds"]
    print(f"Ingerindo dados do Parceiro A para {execution_date}")
    # Lógica de ingestão aqui...
    records = 15000
    return records  # Retorno vai para XCom automaticamente

with DAG(
    dag_id="pipeline_dataflow_v2",
    start_date=datetime(2024, 1, 1),
    schedule_interval="0 2 * * *",  # Todo dia às 2h
    catchup=False
) as dag:

    task_ingest_a = PythonOperator(
        task_id="ingest_parceiro_a",
        python_callable=ingest_parceiro_a,
        provide_context=True
    )

Dependências entre Tasks

Definindo a ordem de execução com >> e <<

MACKENZIE

🔗 Definindo Dependências — Operador >>

O operador >> define a ordem de execução. A >> B significa "B só executa após A ter sucesso".
# Dependência linear
ingest >> validate >> transform >> load

# Dependência com fan-out / fan-in
ingest_a >> validate
ingest_b >> validate
ingest_c >> validate
validate >> transform >> load

# Usando listas (equivalente ao acima)
[ingest_a, ingest_b, ingest_c] >> validate >> transform >> load
RESULTADO VISUAL:

[ingest_a] ──┐
[ingest_b] ──┼──► [validate] ──► [transform] ──► [load]
[ingest_c] ──┘

• ingest_a, ingest_b, ingest_c rodam EM PARALELO
• validate só inicia quando TODOS terminam
• transform aguarda validate
• load aguarda transform
Regra: Sempre usar >> (bitshift). Evitar set_upstream() / set_downstream() — menos legível.

from airflow import DAG
from airflow.operators.python import PythonOperator
from airflow.operators.bash import BashOperator
from airflow.operators.dummy import DummyOperator
from datetime import datetime, timedelta

default_args = {
    "owner": "carlos",
    "retries": 2,
    "retry_delay": timedelta(minutes=5),
    "email_on_failure": True,
    "email": ["carlos@dataflow.com"]
}

with DAG(
    dag_id="pipeline_medallion_v1",
    default_args=default_args,
    start_date=datetime(2024, 1, 1),
    schedule_interval="0 2 * * *",
    catchup=False,
    tags=["dataflow", "medallion"]
) as dag:

    start = DummyOperator(task_id="start")

    ingest_a = PythonOperator(task_id="ingest_parceiro_a", ...)
    ingest_b = PythonOperator(task_id="ingest_parceiro_b", ...)
    ingest_c = PythonOperator(task_id="ingest_parceiro_c", ...)

    transform = BashOperator(task_id="spark_silver", ...)
    gold = BashOperator(task_id="spark_gold", ...)
    notify = PythonOperator(task_id="notify_slack", ...)

    start >> [ingest_a, ingest_b, ingest_c] >> transform >> gold >> notify

XComs

Comunicação entre tasks — passando dados no pipeline

MACKENZIE

📨 XComs — Cross-Communication

XCom permite que tasks troquem pequenas mensagens (metadados, contagens, paths). NÃO usar para DataFrames grandes.
def ingest_parceiro_a(**kwargs):
    """Task que PUSHA um XCom."""
    records_count = 15230
    file_path = "/datalake/bronze/parceiro_a/2024-01-15/"
    
    # Push explícito
    kwargs["ti"].xcom_push(key="records", value=records_count)
    kwargs["ti"].xcom_push(key="output_path", value=file_path)
    
    # Ou simplesmente retornar (vai para key="return_value")
    return {"records": records_count, "path": file_path}

def validate_data(**kwargs):
    """Task que PUXA um XCom."""
    ti = kwargs["ti"]
    
    # Pull explícito
    records = ti.xcom_pull(task_ids="ingest_parceiro_a", key="records")
    result = ti.xcom_pull(task_ids="ingest_parceiro_a")  # return_value
    
    print(f"Validando {records} registros...")
    if records == 0:
        raise ValueError("Nenhum registro ingerido!")
Limites XCom: Máximo ~48KB (SQLite) ou ~1GB (PostgreSQL). Use para metadados, NÃO para dados. Para DataFrames, passe caminhos de arquivo.

📅 Execution Date e Catchup

A execution_date (logical_date) é o início do intervalo de dados que a DAG está processando, NÃO quando ela roda.
DAG com schedule_interval="@daily", start_date=2024-01-01

Dia real: 2024-01-02 às 00:00
├── execution_date = 2024-01-01  (processa dados DO dia 01)
├── data_interval_start = 2024-01-01
└── data_interval_end   = 2024-01-02

Dia real: 2024-01-03 às 00:00
├── execution_date = 2024-01-02  (processa dados DO dia 02)
└── ...

catchup=True (default)

Executa TODAS as datas passadas desde start_date. Útil para backfill.

catchup=False

Executa apenas a data mais recente. Padrão para produção.

Armadilha comum: start_date=datetime(2023,1,1) com catchup=True = Airflow tenta rodar 365+ DAG Runs de uma vez!

Retry e Error Handling

Resiliência em produção — falhas acontecem

MACKENZIE

🔄 Retry — Recuperação Automática de Falhas

Em produção, falhas transitórias (rede, timeout, serviço indisponível) são comuns. Retry resolve 80% sem intervenção humana.
default_args = {
    "owner": "carlos",
    "retries": 3,                          # Tentar 3x antes de falhar
    "retry_delay": timedelta(minutes=5),   # Esperar 5min entre tentativas
    "retry_exponential_backoff": True,     # 5min, 10min, 20min...
    "max_retry_delay": timedelta(hours=1), # Máximo 1h entre retries
    "email_on_failure": True,              # Notificar quando falhar de vez
    "email_on_retry": False,               # Não notificar em retry
    "email": ["carlos@dataflow.com"],
    "execution_timeout": timedelta(hours=2) # Timeout máximo da task
}

# Por task: override de retries
critical_task = PythonOperator(
    task_id="call_external_api",
    python_callable=call_api,
    retries=5,                             # Mais retries que o padrão
    retry_delay=timedelta(minutes=2)
)
Timeline de um retry:
[Tentativa 1] ──FALHA──► espera 5min ──► [Tentativa 2] ──FALHA──►
espera 10min ──► [Tentativa 3] ──SUCESSO ✅

Sem retry: FALHOU → pipeline parado → acordar Carlos às 3h
Com retry: FALHOU → retry automático → sucesso na 3ª tentativa → todos dormem

🚨 Error Handling — Callbacks e SLA

def on_failure_callback(context):
    """Chamado quando a task falha definitivamente."""
    task_id = context["task_instance"].task_id
    dag_id = context["dag"].dag_id
    exec_date = context["ds"]
    error = context["exception"]
    
    # Enviar alerta no Slack
    send_slack_alert(
        channel="#data-alerts",
        message=f"❌ FALHA: {dag_id}/{task_id} em {exec_date}\nErro: {error}"
    )

def on_success_callback(context):
    """Chamado quando a task finaliza com sucesso."""
    print(f"✅ {context['task_instance'].task_id} concluída!")

with DAG(..., on_failure_callback=on_failure_callback) as dag:
    
    task_critical = PythonOperator(
        task_id="ingest_critical",
        python_callable=ingest_data,
        on_failure_callback=on_failure_callback,  # Por task
        on_success_callback=on_success_callback,
        sla=timedelta(hours=1)  # Alerta se demorar mais que 1h
    )
