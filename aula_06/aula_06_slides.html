💬 Uma conversa sobre pipelines confiáveis

Nas últimas semanas nós colocamos a mão na massa: subimos o ambiente, ingerimos dados, criamos DAGs e fizemos o pipeline rodar de ponta a ponta. Hoje damos um passo atrás para olhar o quadro completo.

Esta aula é teórica e discursiva. Não vamos digitar código — vamos entender por que as ferramentas existem, quando usá-las e quais decisões um engenheiro de dados precisa tomar. O código que vocês já escreveram serve de pano de fundo.

Vamos costurar dois temas que, juntos, definem um pipeline maduro:
1) Orquestração avançada — fazer o pipeline pensar e reagir.
2) Qualidade de dados — garantir que o que ele produz é confiável.
Ao longo dos slides você verá caixas "Para discutir". Elas são convites para o debate — pare, pense e defenda um ponto de vista.
MACKENZIE

🧵 O fio condutor: orquestrar bem para confiar nos dados

Um pipeline de dados tem duas perguntas fundamentais por trás dele:

  1. "O trabalho certo aconteceu, na ordem certa, na hora certa?" — é o território da orquestração (Aula 5).
  2. "O resultado desse trabalho é confiável o suficiente para alguém decidir com base nele?" — é o território da qualidade de dados (Aula 6).

As duas coisas se encontram num ponto prático: os quality gates — checagens de qualidade que a própria orquestração executa e usa para decidir se o pipeline segue, para ou alerta alguém. É onde as duas aulas se abraçam.

Parte A — Orquestração Avançada

Fazendo o pipeline pensar, esperar e reagir

Aula 5 · revisão conceitual
MACKENZIE Ideia central

🤖 De pipeline "burro" a pipeline inteligente

Na Aula 4, o pipeline da DataFlow era uma fila reta: extrair → transformar → carregar, sempre igual, todo dia. Funciona — até o dia em que o mundo não coopera.

E o mundo raramente coopera: o arquivo do parceiro atrasa, a segunda-feira tem o triplo do volume, a sexta precisa de um relatório extra, uma fonte falha mas as outras não. Um pipeline linear não sabe lidar com nada disso — ele só executa cegamente.

Orquestração avançada é dar ao pipeline a capacidade de observar o contexto e reagir: escolher caminhos, esperar condições, isolar falhas e chamar as pessoas certas.
💬 Para discutir
  • Pensem no pipeline que vocês subiram na Aula 5. Em que momento ele deixou de ser "uma fila reta"?
MACKENZIE

🔀 Branching — o pipeline que escolhe caminhos

O BranchPythonOperator resolve uma pergunta simples: "dependendo da situação, qual caminho seguir?" Uma função avalia o contexto (o dia da semana, o volume de dados, uma flag externa) e devolve o nome da próxima etapa. Os caminhos não escolhidos são marcados como skipped — não falham, apenas não acontecem.

É a diferença entre uma receita única e uma receita com "se... então...". O pipeline ganha ramificações condicionais.

                        ┌──► processamento_pesado   (volume alto)
[avaliar_contexto] ──►──┤
                        └──► processamento_leve     (volume baixo)
   (decide o caminho)        os demais viram "skipped"
💬 Para discutir
  • Branching escolhe um caminho. E se precisássemos rodar vários caminhos em paralelo — isso ainda é branching? Qual seria a diferença?
MACKENZIE

👁️ Sensors — esperar o mundo externo

Nem tudo está sob nosso controle. O arquivo do parceiro chega "por volta das 6h". Uma outra DAG precisa terminar antes. Uma API precisa responder. O Sensor é um operator que espera uma condição virar verdadeira — ele fica "cutucando" (poll) até conseguir, ou até estourar o timeout.

SensorEspera por...Exemplo na DataFlow
FileSensorum arquivo aparecero CSV de vendas do parceiro do dia
ExternalTaskSensoroutra DAG/task terminara ingestão terminar antes de agregar
Sensores de API/tempouma condição externauma janela de horário, um endpoint no ar
Um sensor mal configurado é perigoso: sem timeout, ele espera para sempre e prende recursos. Esperar é útil; esperar sem limite é um bug.
💬 Para discutir
  • O arquivo do parceiro nunca chegou. O sensor deve falhar o pipeline ou apenas pular a etapa (soft-fail)? De que depende essa escolha?
MACKENZIE

📦 TaskGroups — domando a complexidade visual

Conforme o pipeline cresce, a tela vira um emaranhado de caixas e setas. TaskGroups agrupam tasks relacionadas em blocos — na interface, viram um bloco que abre e fecha. Não muda o que o pipeline faz; muda a legibilidade e a capacidade de raciocinar sobre ele.

Pensem em processar três parceiros: cada um tem "baixar → validar → padronizar". Em vez de nove caixas soltas, você tem três grupos limpos e idênticos — inclusive gerados em um laço.

Legibilidade não é luxo. Um pipeline que ninguém entende é um pipeline que ninguém consegue consertar às 3h da manhã quando ele quebra.
💬 Para discutir
  • Organização "só visual" tem valor real de engenharia? Argumentem a favor e contra.
MACKENZIE Conceito-chave

⚡ Orquestrar não é processar

Este é um dos conceitos mais importantes das duas aulas. O Airflow é o maestro: ele agenda, dispara e monitora. Ele não deve ser o músico que carrega milhões de registros na própria memória — para isso existe o cluster Spark.

O SparkSubmitOperator materializa essa separação: o Airflow submete o job ao cluster e acompanha o status; o processamento pesado acontece no Spark, que foi feito para isso.

   ❌ Anti-padrão                     ✅ Correto
   ┌────────────────┐                ┌───────────┐   submete   ┌──────────────┐
   │ Airflow worker │                │  Airflow  │ ──────────► │ Cluster Spark│
   │ processa 1M    │  → estoura     │ (orquestra│ ◄────────── │ (processa)   │
   │ registros      │    memória     │ e monitora)│   status    └──────────────┘
   └────────────────┘                └───────────┘
💬 Para discutir
  • Para um dataset de 5 MB, faz sentido a complexidade de submeter ao cluster, ou processar "ali mesmo" é aceitável? Onde fica a fronteira?
MACKENZIE

📢 Falhas acontecem — o que importa é a reação

Pipelines maduros assumem que falhas vão ocorrer e se preparam para elas com dois mecanismos:

Callbacks — notificar a pessoa certa

Ao falhar (ou ter sucesso), a task dispara uma função: registrar log, mandar mensagem no Slack, abrir um alerta. A ideia é graduar o alerta pela criticidade — um aviso discreto para um warning, um chamado urgente para uma falha na camada crítica.

Trigger rules — quando uma task deve rodar

Por padrão, uma task só roda se todos os anteriores tiveram sucesso (all_success). Mas às vezes queremos "rode se qualquer um deu certo", ou "rode de qualquer forma para limpar recursos" (all_done). A trigger rule controla essa lógica de fluxo.

💬 Para discutir
  • Alertar demais gera fadiga de alerta (as pessoas param de olhar). Alertar de menos deixa problemas passarem. Como calibrar isso?
MACKENZIE

🧩 Síntese — a orquestração como sistema nervoso

Juntando as peças da Aula 5, o pipeline ganha um "sistema nervoso": ele percebe (sensors), decide (branching, trigger rules), delega o trabalho pesado (SparkSubmit), se organiza (TaskGroups) e avisa quando algo dá errado (callbacks).

RecursoPergunta que responde
BranchingQual caminho seguir agora?
SensorJá posso começar?
TaskGroupComo manter isso legível?
SparkSubmitQuem faz o trabalho pesado?
Callback / trigger ruleO que fazer quando algo muda ou falha?
Mas orquestrar bem não garante dados bons. Um pipeline impecável pode entregar lixo com pontualidade. É aqui que entra a Parte B.

Parte B — Qualidade de Dados

Garantindo que o resultado é confiável o suficiente para decidir

Aula 6 · revisão conceitual
MACKENZIE

💸 "Dados ruins, decisões ruins"

O gatilho da DataFlow foi concreto: um relatório de faturamento mostrou vendas negativas. Investigando, apareceu de tudo — 15% dos registros de um parceiro com valores negativos, milhares de duplicatas de outro, pedidos apontando para clientes que não existem.

O resultado não foi só um número errado numa planilha: foi um relatório errado no conselho. Dados ruins não ficam quietos — eles viram decisões ruins, com custo real.

"Garbage in, garbage out." Se dado ruim entra no pipeline, métrica errada sai do outro lado — com aparência de verdade, o que é ainda pior.
💬 Para discutir
  • Entre um pipeline que atrasa mas entrega dado correto, e um que é pontual mas às vezes entrega dado errado — qual é o pior para o negócio? Por quê?
MACKENZIE

📐 As 6 dimensões da qualidade

"Qualidade" é vago demais para virar ação. Por isso a decompomos em dimensões — cada uma responde a uma pergunta concreta e mensurável:

DimensãoPerguntaViolação típica
CompletudeOs campos obrigatórios estão preenchidos?customer_id nulo em 5% das linhas
UnicidadeHá duplicatas?o mesmo pedido aparece 3 vezes
ValidadeOs valores fazem sentido?valor de venda negativo
ConsistênciaOs dados concordam entre si?entrega antes do pedido
IntegridadeAs referências existem?pedido de cliente inexistente
AtualidadeOs dados são recentes o bastante?última carga há 72h (esperado: diário)
💬 Para discutir
  • Um dado pode ser válido (formato certo, valor plausível) e mesmo assim errado. Como isso é possível? Qual dimensão pega esse caso — e qual não pega?
MACKENZIE

🩺 Validar é diagnosticar, não apagar

Diante de um dado suspeito, o instinto ingênuo é "jogar fora". Mas em engenharia de dados, apagar dado é perder informação — e muitas vezes perder a própria pista do problema.

A postura madura é medir cada dimensão e decidir com base num limite (threshold): "aceito até 2% de nulos neste campo". A validação vira um exame de saúde do dado, com resultado quantitativo, não um chute.

Um bom check responde três coisas: o que falhou, quanto falhou (métrica) e se passou no limite acordado. Sem número, não é qualidade — é opinião.
💬 Para discutir
  • Quem deveria definir os thresholds — o time técnico ou a área de negócio? O que muda conforme a resposta?
MACKENZIE Padrão de projeto

🏥 Quarentena — isolar sem destruir

A resposta da DataFlow para dado ruim não foi deletar: foi colocar em quarentena. Os registros que falham nos checks vão para uma área separada, carregando metadados que contam a história: qual regra falhou, quando, de qual arquivo veio.

[Bronze] ──► [Checks de qualidade] ──┬──► [Silver] (dados que passaram)
                                     │
                                     └──► [Quarentena] + motivo da rejeição
                                            → investigar, corrigir, reprocessar

Assim ninguém perde dado, o pipeline não trava por causa de algumas linhas ruins, e o time ganha material para descobrir a causa raiz — muitas vezes um problema na origem, não no dado em si.

💬 Para discutir
  • A quarentena vive crescendo e ninguém olha. Que processo ou responsabilidade evita que ela vire um "cemitério de dados"?
MACKENZIE

📊 Tornar a qualidade visível

Qualidade que ninguém enxerga não muda comportamento. Por isso cada execução gera um relatório: quantos registros entraram, qual o score de cada check, o que passou, o que falhou, quanto foi para quarentena.

RELATÓRIO DE QUALIDADE — 2024-01-15
Total analisado: 152.340
  Completude order_id ....... 100.0%  (limite 98%)  ✅
  Unicidade (order_id) ......  97.9%  (limite 99%)  ❌
  Validade valor > 0 ........  91.8%  (limite 95%)  ❌
  Integridade cliente .......  99.7%  (limite 99%)  ✅
RESULTADO: ❌ 2 checks falharam · Quarentena: 8,3%

Guardando esses relatórios ao longo do tempo, surge algo valioso: tendência. Um score que cai lentamente semana após semana avisa de um problema antes de ele virar crise.

💬 Para discutir
  • O que é mais útil: um relatório de "hoje" ou a curva dos últimos 30 dias? O que cada um revela?

Parte C — Onde tudo se encontra

Quality gates: quando a orquestração usa a qualidade para decidir

Aulas 5 + 6 · integração
MACKENZIE A ponte entre as aulas

🚦 Quality Gate — a qualidade vira decisão do pipeline

Aqui as duas aulas se fundem. Lembram do branching da Aula 5? Um quality gate é exatamente isso, mas a decisão é baseada na qualidade dos dados: o pipeline roda os checks e, conforme o resultado, decide se segue, para ou alerta.

[ingestão] ──► [checks de qualidade] ──► (quality gate / branch)
                                              │
                                    passou ───┼──► [transformar → Silver/Gold]
                                              │
                                    falhou ───┴──► [alertar + parar]

A orquestração fornece o mecanismo (branch, callbacks). A qualidade fornece o critério (os scores). Sozinhos, cada um é incompleto; juntos, formam um pipeline em que dado ruim não avança calado.

MACKENZIE

🎚️ Nem todo gate é igual — 3 posturas

A rigidez do gate depende de onde ele está no pipeline. Quanto mais perto da decisão de negócio, mais rígido:

ModoAção ao falharOnde faz sentido
Monitorsó registra e medeentrada (Bronze) — ainda estamos observando
Lenientmanda o ruim para quarentena e seguemeio (Bronze → Silver)
Strictbloqueia o pipeline e alertasaída crítica (Silver → Gold → dashboard)
Regra da DataFlow: "Dado ruim nunca chega na Gold. Melhor não publicar do que publicar errado." Perto do board, o gate é sempre strict.
💬 Para discutir
  • Bloquear o pipeline também tem custo (dashboard desatualizado, gente esperando). Quando parar é pior do que deixar passar um dado imperfeito?

🧪 Estudo de caso — vamos decidir juntos

São 5h50. A DAG diária da DataFlow está rodando. O cenário:

  • O arquivo do Parceiro A ainda não chegou (o sensor está esperando).
  • O Parceiro B chegou, mas com 4% de valores negativos (limite de validade: 2%).
  • O Parceiro C chegou perfeito.
  • Às 6h30 sai o relatório que Roberto leva ao conselho.
💬 Para discutir — em grupos
  • O sensor do Parceiro A deve segurar todo o pipeline, ou os outros seguem sem ele?
  • Os 4% do Parceiro B: quarentena parcial e segue, ou bloqueia? Qual modo de gate?
  • Que alertas disparam, e para quem, em cada decisão?
  • O que aparece no relatório das 6h30 em cada uma das escolhas?
MACKENZIE

🎓 O que levar desta aula

Um pipeline profissional não é o que funciona no dia bom — é o que se comporta bem no dia ruim: quando o arquivo atrasa, o volume explode, uma fonte falha e os dados chegam sujos.

A orquestração avançada dá ao pipeline reflexos para reagir ao contexto. A qualidade de dados dá a ele consciência do que está produzindo. E os quality gates são onde essas duas capacidades viram uma só decisão: seguir, isolar ou parar.

Confiabilidade não é um recurso que você liga no fim. É uma postura de projeto — pensada desde a primeira DAG e defendida em cada camada.
